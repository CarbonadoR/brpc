# JFS 阶段 4：固定首选、4备选与首选等待

## 实现边界

- 默认使用完整 SocketId 经 Mix64 映射到固定首选；同一链路反复发送首先复用该 JFS。
- 备选从 pthread TLS xoshiro256++ 状态采样，4个互异且不包含首选；池大小不足6时枚举其余JFS。TLS只存随机数状态，不独占JFS。
- 只读取候选 sq_inflight 选择最小者，不执行容量CAS，不在全池搜索。首选和一个备选各尽可能接收前缀；一次准备节点上限32，不等待凑批。仅软件接收允许并发窗口内超量，硬件提交受独立计数限制。
- 已接收部分返回正字节数；剩余由 Socket 再尝试，零进展时返回 -1/EAGAIN。IOBuf和seq只推进实际接收部分。
- KeepWrite 使用原Socket butex，等待节点由其栈帧持有。节点登记在固定首选的等待列表；每个JFS只用一个专门的等待列表mutex保护登记、注销和通知，不包围post/poll。
- 登记后复查首选容量，避免漏通知。owner先推进已接受请求，再在有接纳空间时唤醒一个等待者；关闭/故障唤醒所有。取消和通知在同一个JFS等待锁下完成，不保留栈节点裸指针到锁外。
- 关闭先拒绝新操作、通知各JFS的等待者，并等返回中的等待guard退出，之后才释放资源。
- 为已有配置保留 `urma_jfs_affinity=false` 的按批轮询入口；默认开启，性能对比使用默认固定首选方案。

## 验证

Bazel mock 共67项通过。新增覆盖：池大小1/2/5/6/16，随机候选去重和排除首选；固定采样重放最小inflight选择；未采样空闲队列不会触发全池回退；首选和备选部分接收后下一次EAGAIN且不多消费；备选CQE不唤醒首选等待者。

已有共享SQ不同Socket通知、登记/释放竞态200次、超时/取消、关闭期间栈guard回收测试继续覆盖，并改为只登记首选。

真机：145服务端/151客户端，NUMA3 CPU288–303、udmac1d1e2、event/multi；8 JFS/SQ16、2 JFR/RX512，32条独立链路、QD64，1K/8K/100K对称消息各50 iterations。命令及日志保存在项目外层 `测试/阶段4_真机验证_20261104/`；短用例仅验证收发和错误，不用于比较时延。
